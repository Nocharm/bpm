## 1. 목표 · 비목표

- 목표: 한 노드의 **같은 변(핸들)**에 2개 이상 엣지가 붙을 때, 선·라벨이 핸들 근처에서 겹치지 않고 반경이 다른 아크로 펼쳐지게 한다. 노드 타입 무관, 세 선 모양(`""`/`smoothstep`·`default`·`straight`)과 LR/TB 모두.
- 비목표: 변(핸들 side)을 바꾸지 않는다(비교 화면 주석이 기록한 4변 그리디 회피의 꼬임 재발 방지, `compare/page.tsx:1031-1035`). 저장 데이터·백엔드·서명(`framework_confirm.py:57`, `change-summary-section.tsx:132-146`)을 건드리지 않는 **렌더 전용 파생**이다. 서로 다른 변에서 기하학적으로 가까워지는 엣지(작은 마름모의 top/right 등)는 대상이 아니다.

## 2. 현행 사실 (조사 요약)

- 앵커는 (변, 방향)당 DOM 핸들 1개. `s-<변>`/`t-<변>`는 같은 style로 같은 픽셀(`process-node.tsx:1103-1130`). RF는 핸들 박스 바깥변 중점을 모든 엣지에 동일하게 준다(`@xyflow/system index.js:1420-1437`). 서브프로세스는 `in`(좌) 1개 + `__primary__` 또는 끝별 핸들(우, 2개 이상이면 `(i+1)/(n+1)%` 분산)(`process-node.tsx:1047-1092`).
- 에디터 엣지 컴포넌트는 좌표 6개만 쓰고 `data`·`id`·`sourceHandleId`를 읽지 않는다(`multiline-edge.tsx:29-39, 65-94`). 꺾은선은 app 소유 우회(`edge-detour.ts`)가 RF 헬퍼 앞에 끼어든다.
- RF 꺾은선은 핸들 앞 20px 스텁 + 중앙 회랑이 같은 핸들의 모든 엣지에서 동일 → 세로 구간·트렁크·화살촉·라벨이 포개진다. 곡선은 끝 접선이 모두 변에 수직이라 마지막 ~40px 포개짐. 직선은 화살촉만 겹침. 동측(top→top) 루프백은 RF offset 20으로 완전히 포개짐.
- 실데이터(`backend/dev.db`, 697엣지): 같은 타깃 핸들 공유 43그룹(93엣지, `in` 15·`t-left` 16·`t-bottom` 12, 최대 4), 같은 소스 핸들 공유 35그룹(`s-right` 18·`s-bottom` 16, 최대 3). 선 모양은 683/697이 `""`(꺾은선 렌더).
- 수렴은 구조적: 드래그 생성도 `s-right`/`t-left` 강제(`page.tsx:3705-3720`), CSV 임포트 right/left 고정, 자동정렬 back 엣지는 `top`(LR)으로 모임(`flow-layout.ts:127-152`).
- 엣지를 그리는 경로 4벌: (a) `EDITOR_EDGE_TYPES`(에디터 main·임베드 자식·게이트웨이·sp-ends·ghost 전부 한 인스턴스) (b) 비교 `LabeledSmoothEdge`/`RemovedArcEdge`(`compare/page.tsx:161-231`) (c) RF 내장 SmoothStepEdge(인터뷰 미리보기·제안 카드·캠페인 연결 캔버스, edgeTypes 없음) (d) SVG `ScopePreview`(중심→중심 직선 + 역행 24px 통로, `scope-preview.tsx:39-49`). 이번 범위는 (a)(b) + (d)의 역행.
- 에디터 유일 변환 지점 = `styledEdges` useMemo(`page.tsx:7433-7612`), 최종 배열 `[main, child, gateway, synthetic]` → `anchorEdgesToGhosts`. 드래그 중에는 `nodes` state가 동결되고 RF 스토어만 움직인다(드래그 성능 라운드).
- 화살촉 ArrowClosed 12.5 strokeWidth 단위, 촉 끝 = 경로 끝점, 1.5px 선에서 약 4.7×7.5px. 히트 path 20px. 노드가 엣지 위에 그려지므로 끝점을 노드 안쪽으로 밀 수 없고, 벌림은 변과 평행한 방향만 가능.

## 3. 설계

### 3.1 용어

- **앵커 그룹**: 같은 노드의 같은 앵커에 붙는 엣지 끝들의 집합. 키 = `nodeId | side | (변 id가 아니면 handleId)`. `s-left`와 `t-left`는 같은 그룹(같은 픽셀), 서브프로세스 `in`/`__primary__`/끝별 핸들은 각각 별도 그룹.
- **끝 프레임**: 앵커를 원점으로 `u` = 진입축(타깃 끝은 노드 안쪽 +, 소스 끝은 노드 바깥쪽 +), `v` = 변과 평행한 측면축. 상대 끝의 좌표 `(u_o, v_o)`로 분류·정렬한다.
- **가족**: 측면 부호 `sign(v_o)` × {대향(`u_o < -(R0+STUB)`), 동측(그 외)}. 대향 = 흐름 방향에서 들어오는 일반 엣지, 동측 = 루프백·같은 줄 옆 노드.
- **레인 k, 반경 r_k = R0 + k·GAP**: 아크 반경이자 레인(핸들 앞 마지막 회랑)까지의 거리.

### 3.2 레인 배정 — 순수 함수 `assignFanLanes(edges, geom)` (`frontend/src/lib/edge-fanout.ts`)

1. 입력: RF Edge 배열(ghost 재매핑 후, `hidden` 제외)과 노드 기하 `id → {x, y, w, h, nodeType}`. 상대 끝 앵커는 실측 핸들이 없으므로 **추정치**로 잡는다: 좌/우 변은 `y + 18`(process/subprocess) 또는 `y + h/2`(decision·start·end), 상/하 변은 `x + w/2`. `ctrl-ghost:` 접두는 벗겨 원본 노드 기하를 쓴다.
2. 각 엣지의 두 끝을 각자 앵커 그룹에 넣는다. 그룹 크기 1이면 팬 없음.
3. 그룹 안에서 가족별 정렬 → k 부여. **대향 가족은 |v_o| 큰 순(먼 소스가 안쪽)**, **동측 가족은 |v_o| 작은 순(가까운 소스가 안쪽, 무지개)**. 각각 교차가 생기지 않는 유일한 순서(목업 블록1·3). 같은 측면에 둘 다 있으면 **동측이 안쪽(기저 34)**, 대향은 그 바깥에서 시작한다(리뷰 C3 — 반대로 두면 루프백 통로가 하강 엣지를 자른다). 동률은 `edge.id` 오름차순(결정적, 드래그 프레임 간 플립 방지 — 우회 타이브레이크와 같은 이유).
4. |v_o| < 4px(같은 줄)면 k = -1: 아크 없이 직선 진입(트렁크 소유자). 나머지는 이 엣지를 비켜 간다.
5. **반경 r을 배정 단계에서 확정한다**(리뷰 C1·C2·C4·C7). 공칭 `base + 10k`를 형제의 제약(측면 거리 − 6, 대향은 수평 여유 `(u − 20 − 11)/2`, 11 = 핸들 박스 돌출 5.5×2)에 맞춰 **바깥(가까운 소스)부터 안으로 압축**하되 인접 레인 간격은 최소 6px. 여유가 6px 미만이면 그 끝은 `r = 0`(팬 없음, 현행 경로). 반경을 끝마다 따로 클램프하면 안쪽·바깥 순서가 뒤집혀 교차하고, `r = |v|`가 되면 0길이 구간이 `NaN` 경로를 만든다. 하위프로세스 끝 핸들은 `handleTops`((i+1)/(n+1))로 실위치를 써 정렬한다(리뷰 C6).
6. 출력: `Map<edgeId, { s?: FanLane; t?: FanLane }>`, `FanLane = { k, idx, n, r }` (`idx`/`n`은 그룹 전체 안의 결정적 순번·크기, 직선 끝점 분산용).
6. 비용 O(E log E). 에디터는 `styledEdges` 재계산 때만(엣지·노드 state 변경), 드래그 프레임에서는 돌지 않는다.

### 3.3 경로 생성 — 엣지 컴포넌트가 `data.fan`을 읽어 라이브 끝점으로 그린다

공통: 컴포넌트는 RF가 준 라이브 `sourceX/Y·targetX/Y·positions`와 `data.fan.{s,t}.k`만 쓴다. 대향/동측 분류는 라이브 좌표로 다시 판정한다(드래그 중 k는 동결, 모양은 좌표를 따라감).

**라이브 검증**: 컴포넌트는 배정 반경 `lane.r`을 라이브 좌표로 다시 확인한다 — `min(lane.r, R_MAX, |v| − 6, 대향이면 (u − 20)/2)`가 `lane.r − 2`보다 작으면(추정보다 빡빡) 팬을 포기하고 현행 경로. 0길이 구간은 라우트 단계에서 제거(방어). 소스·타깃 양쪽이 팬이면 각각 독립 검증.

**꺾은선(`smoothstep`, 레거시 `""`)** — "게이트 포인트 + 아크":
- 타깃 끝 게이트 `G_t = (u=-r_t, v=side·r_t)`. 경로는 `… → G_t` 에 측면축을 따라(v→0 방향) 도착한 뒤 원호 `A r_t r_t 0 0 sweep E`로 핸들에 접선 진입. 소스 끝은 거울: `S → A r_s … → G_s = (u=r_s, v=side·r_s)`에서 측면축으로 이탈.
- 게이트 사이(또는 소스 끝점↔게이트)는 소형 직각 라우터 `routeOrth(P, d1, Q, d2)`: 출발 방향 `d1`, 도착 방향 `d2`가 (i) 직교면 모서리 1개 `(P→코너→Q)`, (ii) 같은 방향이면 모서리 2개(첫 코너는 `STUB` 뒤, RF 혼합 케이스와 같은 모양), (iii) 반대 방향이거나 코너가 진행 방향 뒤에 놓이면 **null → 팬 없음(현행 경로)**. 실데이터 조합(우→좌 대향, 하→좌 분기, top→top 루프백, TB 하→상)은 (i)(ii)로 덮인다.
- 내부 모서리는 기존 `buildRoundedOrthPath`의 5px Q 라운드, 양끝 아크만 진짜 원호(`A`) — 반경 30~60px에서 Q(포물선)는 덜 둥글어 중첩 원호 느낌이 약해진다.
- 라벨 앵커: 아크를 뺀 직선 구간 중 최장·무가림 구간 중앙(현행 규칙 재사용). 대향 팬에서는 소스 행 수평 구간이라 자연히 흩어진다(목업 블록1 A).
- **장애물 폴백(에디터만)**: 팬 폴리라인의 직선 구간을 캐시된 장애물(`getObstacles`, 양끝 노드 제외)과 `crossesH/crossesV`로 검사, 하나라도 관통하면 그 엣지는 현행 경로(우회 또는 RF)로 그린다. 우회 로직 자체는 변경 없음. 비교 화면은 장애물 검사 없이 팬(읽기전용·자동 배치).

**곡선(`default`)** — 자체 cubic 문자열 `M S C C1 C2 E`:
- 제어점은 각 끝의 변 법선 위. 기본 거리는 RF와 동일(`0.5·distance`, 역방향은 `curvature·25·√(-distance)`). **팬 끝만** `c = 1.2·r`로 당겨 반경 다른 중첩 아크가 되게 한다(목업 블록1·2 곡선 A). 끝점 유지. 라벨은 t=0.5 지점.

**직선(`straight`)** — 끝점을 변과 평행하게 `(idx - (n-1)/2)·SPREAD` 이동, `±(HANDLE/2 - 1) = ±4.5px`로 클립(핸들 11px 안). 각도가 이미 다르므로 이것으로 화살촉 포개짐만 푼다.

### 3.5 파라미터 (단일 소스 `edge-fanout.ts` 상수)

| 이름 | 값 | 근거 |
|------|----|------|
| `R0` | 14px | 첫 아크 반경. 20px 스텁보다 짧아 촘촘한 배치에서도 성립 |
| `GAP` | 10px | 레인 간격. 화살촉 7.5px보다 크고, 목업에서 1.5px 선이 또렷이 갈라짐 |
| `R_MAX` | 64px | 5레인 초과는 노드 크기를 넘어 어색 |
| `R_MIN` | 6px | 이보다 측면 거리가 작으면 아크 무의미 → 현행 경로 |
| `STUB` | 20px | RF 스텁과 동일(첫 코너 최소 거리) |
| `SPREAD` | 3.5px | 직선 끝점 간격, 핸들 11px 안에 3~4개 |

### 3.6 SVG 미리보기 적용 가능성 (사용자 질문)

가능하다. ScopePreview는 핸들이 없고 정방향 엣지는 중심→중심 직선을 타깃 박스에서 자르므로 소스가 다르면 이미 각도로 갈라진다. 겹치는 건 **역행 엣지**뿐(같은 소스 위 중심에서 출발하고 `yTop`도 같음, `scope-preview.tsx:39-49`). 이 역행 엣지에 §3.2의 동측(무지개) 규칙을 적용해 통로 높이를 레인별로 나눈다. 소비처 4곳(피크·노드 요약 모달·임포트 리포트 미리보기·조상 창)이 한 컴포넌트를 쓰므로 한 곳 수정으로 끝난다.

### 3.7 성능 · 드래그 · 라벨 · 히트 영역

- 레인 배정은 O(E log E) 1회, 드래그 프레임에서는 안 돈다. 컴포넌트 기하는 O(1). 장애물 검사는 팬 엣지(약 13%)만, 기존 밴드 프루닝된 캐시 사용. 곡선·직선 컴포넌트는 스토어 구독을 새로 늘리지 않는다.
- 드래그 중: k 동결 + 라이브 좌표. 드롭 후 재배정에서 레인이 바뀔 수 있는 한 번의 점프는 허용(결정적 정렬이라 깜빡임은 없음).
- 라벨: 꺾은선은 소스 행 구간으로 흩어지고 곡선은 t=0.5가 아크 반경 차만큼 벌어진다. 완전 분리는 보장하지 않는다(기존 `pw-measure-edge-label-overlap.mjs`로 회귀 측정).
- 히트 영역 20px는 레인 간격 10px보다 넓어 인접 레인의 hover가 겹칠 수 있다(현행은 완전 동일 위치라 지금보다 나빠지지 않음). 선택 강조(3.5px + 글로우)는 그대로.

### 3.8 변경하지 않는 것

- `QuickConnectLine` 미리보기 선(형제 정보 없음, 이미 5.5px 어긋남 `quick-connect-line.tsx:76-77`), 인라인 라벨 편집 박스 위치(`page.tsx:5805-5817`, 경로와 독립 계산 — 기존과 동일), RF 내장 엣지 표면 3종(인터뷰 미리보기·제안 카드·캠페인 연결 캔버스), 핸들 side 배정 3곳, 백엔드 모델·스키마, 맵별 on/off 토글(요청 없음 → 추가 안 함).

## 5. 리스크 · 완화

- **드래그 중 가족 플립**: 소스를 끌어 대향↔동측 경계를 넘기면 k는 동결된 채 모양만 바뀌어 잠깐 교차할 수 있음 → 드롭 시 재배정. 허용.
- **곡선 팬의 교차 보장 없음**: cubic은 원호가 아니라 극단 배치(소스가 매우 가깝고 |v| 큰 경우)에서 스칠 수 있음 → 목업 확인 범위 안에서는 미발생, 스모크에 케이스 포함.
- **라벨 알약 겹침 잔존**: 곡선 t=0.5 라벨은 아크 차만큼만 벌어짐 → 회귀 측정만, 추가 설계 없음.
- **`useNodes` 구독 범위**: 꺾은선 컴포넌트가 이미 구독 중이라 신규 비용 없음. 곡선·직선은 `data.fan`만 읽어 구독 없음.
- **비교 화면 세션 드래그**: `handleSides`처럼 `nodeCenters` 변경 시 레인도 재계산되어 끌면 순서가 바뀔 수 있음(현행 변 배정도 같은 성질).
