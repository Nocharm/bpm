# 메일 초안 — 컨설턴트 전달 데이터 인터페이스(안) 공유

> **여기 스키마는 저희 쪽 참조 형식(canonical)이며, 실제 산출물 스키마가 확정되면 변환은 저희가 맞춘다** — 필요한 정보 항목의 정의로 읽으면 된다. 근거 설계: `docs/design/2026-08-08-consultant-hierarchy-design.md`.

안녕하세요.

전사 프로세스 7단계 체계 산출물을 사내 BPM 시스템으로 수용하기 위한 준비 현황과, 전달 데이터에 필요한 정보 항목 정의(안)를 공유드립니다. 인터뷰 설계와 산출물 스키마 협의에 참고 부탁드립니다.

## 1. 수용 방향 요약

- **7단계 ↔ 시스템 매핑** — 레벨 1~5는 카테고리(분류 트리), **레벨 6 = 프로세스맵 1개**, 레벨 7 = 맵 안의 업무 노드로 수용합니다. 레벨 6 간 연계업무는 맵 사이의 참조 링크(연계 노드)로 표현됩니다.
- **파라미터는 레벨 6 단위** — 소요시간·비용·인원·연간횟수·FTE와 Input/Output을 맵 단위 속성으로 받습니다.
- **적재는 일괄 자동** — 전달받은 데이터를 시스템이 일괄 적재하며, 맵마다 **오너(해당 업무 인터뷰이)·승인자·공개범위**를 세팅하고 초판(v1)을 게시 상태까지 만들어 둡니다. 적재 이후의 수정·게시는 현업이 시스템 안에서 기존 절차(편집 → 승인 → 게시)로 이어갑니다.
- **재전달(수정본) 언제든 가능** — 맵 코드 기준으로 기존 맵과 매핑해 **변경된 맵만 새 버전으로 반영**하고, 무변경 맵은 건드리지 않습니다. 현업이 시스템에서 수정 중이어도 충돌 없이 이력으로 쌓이며, 반영 전 시뮬레이션(dry-run) 리포트로 변경 내역을 상호 확인할 수 있습니다.

## 2. 전달 데이터 인터페이스(안)

파일 2종입니다. 실제 산출물 형식(DB 덤프·엑셀 등)이 정해지면 변환은 저희가 대응하므로, **아래는 "어떤 항목이 있어야 하는가"의 정의**로 봐주시면 됩니다.

### 2-1. 카테고리 (레벨 1~5) — `categories.json` 1파일

```json
{
  "categories": [
    { "code": "PUR",     "name": "구매", "level": 1, "parent": null },
    { "code": "PUR-SRC", "name": "소싱", "level": 2, "parent": "PUR" }
  ]
}
```

| 항목 | 설명 |
|------|------|
| `code` | 카테고리 고유 코드. **한 번 부여하면 재전달 시에도 불변** |
| `name` | 카테고리명 |
| `level` | 1~5 |
| `parent` | 상위 카테고리 code (레벨 1은 null) |

### 2-2. 프로세스맵 (레벨 6~7) — 맵 1개 = 레코드 1건 (`maps.jsonl`, 1줄 1맵)

```json
{
  "code": "CM-PUR-001",
  "name": "원자재 구매요청 접수",
  "category": "PUR-SRC-REQ-ORD-RAW",
  "owner": "hong.gildong",
  "approvers": ["kim.cheolsu"],
  "department": "Management Center/Purchasing Office/Sourcing Team",
  "visibility": "public",
  "params": {
    "duration": "1.30", "cost_krw": "500000", "cost_usd": "",
    "headcount": "3", "annual_count": "1200", "fte": "1.5",
    "input": "구매요청서(PR)", "output": "발주서(PO)"
  },
  "nodes": [
    { "code": "N1", "name": "구매요청서 접수", "type": "process",  "seq": 1,
      "department": "", "assignee": "", "system": "" },
    { "code": "N2", "name": "예산 승인 확인", "type": "decision", "seq": 2,
      "department": "", "assignee": "", "system": "" }
  ],
  "edges": [
    { "from": "N1", "to": "N2", "label": "" }
  ],
  "links": [
    { "to_map": "CM-PUR-002", "after_node": "N2" }
  ]
}
```

| 항목 | 설명 |
|------|------|
| `code` | **맵 고유 코드 — 재전달 매핑 키.** 한 번 부여하면 불변이어야 합니다 |
| `name` | 맵(레벨 6 업무) 이름. 중복 허용 — 구분은 카테고리 경로가 담당 |
| `category` | 소속 레벨 5 카테고리 code |
| `owner` | 오너 = 해당 업무 인터뷰이의 **사내 계정 ID** |
| `approvers` | 승인자 사내 계정 ID 목록 (이후 버전 게시 결재선) |
| `department` | 담당 부서 경로 |
| `visibility` | `public`(전사 공개) / `private`(권한자만) |
| `params` | 레벨 6 파라미터 — 아래 표기 규칙 참조 |
| `nodes` | 레벨 7 업무 목록 — `type`은 `process`(일반)/`decision`(분기), `seq`는 순서 |
| `edges` | 노드 간 흐름. **생략하면 `seq` 순서로 자동 직렬 연결**, 분기가 있으면 명시(분기 라벨은 `label`) |
| `links` | 연계업무 — 대상 맵 `to_map`(code)과 부착 지점 `after_node`(생략 시 마지막 노드 뒤) |

### 2-3. 표기 규칙

- **duration** — `H.MM` 형식, 소수부는 분. 예: `1.30` = 1시간 30분.
- **비용** — `cost_krw` / `cost_usd` 중 **한쪽만** 입력 (동시 입력 불가).
- **annual_count(연간횟수)·fte** — 연계 단위 값. 이 업무를 호출하는 연계(links)가 있어야 반영됩니다.
- **input / output** — 자유 텍스트, 길이 제한 없음.
- 계정 ID(owner·approvers)는 사내 인사 데이터와 매핑됩니다. 미등재 인원은 적재 시 경고 리포트로 표면화되므로, **명단은 사내 계정 기준으로** 정리 부탁드립니다.

## 3. 인터뷰 시 확보가 필요한 항목 (정리)

1. 레벨 6 업무별 **고유 코드** 부여 체계 (불변 유지)
2. 레벨 1~5 분류 경로 (코드 + 명칭)
3. 업무별 **인터뷰이 사내 계정**(오너) / **승인자** 명단
4. 담당 부서
5. 레벨 7 업무 목록 — 순서, 분기 여부(분기 조건 라벨)
6. 연계업무 — 어느 업무에서 어느 업무로, 흐름상 어느 지점 뒤인지
7. 레벨 6 파라미터 — 소요시간·비용(통화 택1)·인원·연간횟수·FTE·Input/Output

## 4. 협의 요청 사항

1. 산출물 실제 스키마(테이블 정의/컬럼) 초안 공유 시점 — 확정되면 저희가 변환 어댑터를 준비합니다.
2. 인원 식별 기준 협의 — 사번/이메일/계정 ID 중 어느 값으로 명단을 주실지.
3. 전달 주기(전체/부분 재전달 방식)와 검토 사이클.

샘플 데이터 파일을 함께 첨부드리니 형식 감을 잡는 데 참고 부탁드립니다. 문의 주시면 상세 설명드리겠습니다.

감사합니다.
