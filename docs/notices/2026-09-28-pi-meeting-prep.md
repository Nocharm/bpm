# 프로세스맵 시스템(BPM) 현황과 컨설팅 산출물 운영 방식 결정 요청

작성 2026-09-28 · 대상: PI팀 회의(의사결정자용)

> 이 문서의 수치와 인용은 저장소 기록 기준(2026-09-24 커밋)입니다. 기술 근거는 맨 뒤 부록에 따로 두었습니다. 계약 범위·PI팀 내부 입장은 저희가 알 수 없어 반영하지 않았습니다.

## 1. 결정이 필요한 것

**컨설팅이 끝난 뒤, 전사 프로세스맵의 "원본"을 어디에 둘 것인가.**

- 원래 합의(2026-08-09 컨설팅사에 공유): 컨설턴트가 인터뷰 결과를 넘기면 BPM에 한 번에 적재하고, 그 뒤의 수정·승인은 현업이 BPM 안에서 한다.
- 현재 상황: 컨설턴트 쪽이 자기 도구에서 맵을 그리고 승인까지 하며, BPM은 보기 전용으로 쓰고, 이후 수정·개선도 자기 쪽에서 이어가겠다는 입장.
- 이대로 가면 BPM에서 누가 고쳐도 다음 전달본에 덮이고, 계약이 끝나면 고칠 경로 자체가 사라진다.

**추천: 계약 중에는 컨설턴트가 원본을 들고 작업하되, 계약 종료 시 마지막 전달로 BPM이 원본이 된다고 지금 명문화한다.** 추가 개발 없이 현재 시스템으로 가능하다.

## 2. BPM은 지금 무엇을 할 수 있나 (쉬운 말로)

- **그린다**: 업무 흐름을 상자와 화살표로 그리고, 단계마다 담당 역할·부서·사용 시스템·입력물·출력물·소요시간·비용을 적는다.
- **버전을 관리한다**: 현재 모습(As-Is)과 개선안(To-Be)을 따로 두고 나란히 비교한다. 무엇이 추가·삭제·변경됐는지 색으로 보이고, AI가 결재자용 요약을 써 준다.
- **결재한다**: 초안 → 승인 요청 → 결재자 전원 승인 → 게시. 반려·회수·단계별 코멘트가 기록으로 남는다.
- **권한을 나눈다**: 맵마다 오너·편집자·열람자·결재자가 있고, 공개 범위를 정한다. 권한 변경도 승인 절차를 탄다.
- **전사 업무 체계로 묶는다**: 컨설턴트의 7단계 체계(대분류 1~5단계 → 업무 6단계 → 세부 업무 7단계)를 그대로 받아 트리로 탐색하고, 6단계 업무 사이의 연결도 그린다. 다른 부서 업무와의 연결(유관부서 업무)도 표현한다.
- **사람·조직 변화를 따라간다**: 인사 시스템과 자동 연동돼 퇴직·조직개편이 반영되고, 낡은 담당자·부서가 남은 맵을 찾아 한 번에 정리한다.
- **가져오고 내보낸다**: 컨설턴트 인터뷰 파일·CSV·Word를 읽어 들이고, 그림·엑셀·CSV·Word로 내보낸다. 들여오기 전에 "무엇이 바뀌는지" 미리보기 검증을 한다.
- **AI가 돕는다**: 대화로 맵을 만들거나 고치고, 문서 없이 담당자 설문으로 업무 묶음 하나를 채우고, 결재 요청 사유 초안을 써 준다.
- **운영 기반**: 사내 로그인 연동, 매일 자동 백업(14일 보관), 알림·받은함, 운영 대시보드, 사용자·관리자 매뉴얼(한/영, 슬라이드 포함).

## 5. "소스코드를 주겠다"에 대한 현실적 한계

컨설턴트 쪽이 자기 도구의 소스코드를 넘기겠다고 한 것으로 알고 있습니다. 코드를 받는 것과 그 시스템을 사내에서 운영하는 것은 다른 일입니다.

- **돌릴 환경을 새로 만들어야 함**: 저쪽 도구는 저쪽 서버·데이터베이스·로그인 위에서 돌아갑니다. 사내 로그인·인사 데이터·백업 체계와 연결돼 있지 않아, 받는 순간 "설치부터 다시"입니다.
- **아는 사람이 사내에 없음**: 코드는 설명서·테스트·설계 기록이 함께 와야 고칠 수 있습니다. 만든 사람이 떠난 뒤 그 코드를 이해하는 데 드는 시간은 새로 만드는 시간과 크게 다르지 않은 경우가 많습니다.
- **점검 항목이 생김**: 라이선스, 제3자 구성요소, 보안 취약점, 개인정보 처리 방식을 사내 기준으로 다시 검토해야 합니다.
- **결국 두 시스템을 관리하게 됨**: BPM과 넘겨받은 도구가 같은 데이터를 따로 들고 있게 되고, 어느 쪽이 맞는지 판단하는 일이 상시 업무가 됩니다.
- **정리하면**: 소스코드 인수는 "원본을 저쪽에 둔다"의 해법이 아니라, 저쪽의 유지보수 부담을 사내로 옮기는 것입니다. BPM은 이미 사내에 코드·문서·자동 테스트가 있고 운영 중입니다.

## 6. 저쪽 진행 상황에서 보이는 공백

- 현재 인터뷰는 대분류(5단계) 단위로 진행 중이고, **다른 대분류에 속한 업무 사이의 연결(유관부서 업무)은 아직 작업되지 않았으며 이후 계획도 없는 상태**입니다.
- 전사 프로세스맵의 가치는 부서 안 흐름보다 부서 사이 흐름에서 나옵니다. 이 부분이 비면 "부서별 그림 모음"에 그칩니다.
- BPM은 이 연결을 표현하는 방식(다른 대분류 업무를 참조하고, 아직 없는 업무는 자리표시자로 두었다가 나중에 자동 연결)을 이미 만들어 컨설턴트에게 제안해 둔 상태입니다.
- 원본이 BPM에 있어야 이 공백을 사내에서 메울 수 있습니다. 저쪽 도구가 원본이면 저쪽이 계획을 세울 때까지 기다려야 합니다.

## 7. 계약 이후 관리: 실제로 생기는 일들

| 이런 일이 생기면 | BPM이 원본일 때 | 컨설턴트 도구가 원본일 때 |
|---|---|---|
| 담당자 퇴직·조직개편 | 자동 감지 → 오너에게 알림 → 관리자가 한 번에 교체 | 수정 요청 메일 → 재전달 대기 (계약 후엔 불가) |
| 업무 절차가 바뀜 | 담당자가 초안 → 결재 → 게시, 이전 버전과 비교 가능 | 위와 같음 |
| 새 업무가 생김 | 맵을 만들어 체계에 연결(승인) | 위와 같음 |
| 업무가 없어지거나 합쳐짐 | 승인 절차로 자리 정리, 연결된 곳 자동 갱신 | 위와 같음 |
| 대분류 하나를 다시 정비 | AI 설문으로 담당자와 함께 재구성 | 컨설턴트 재계약 |
| 감사·심사에서 이력 요구 | 버전·결재·코멘트 이력 출력 | 저쪽 도구 접근 필요 |
| 데이터 유실 | 매일 자동 백업 14일, 휴지통 복구 | 저쪽 정책에 의존 |

## 8. 회의에서 결정·확인할 것

1. **이양 시점 합의**: 계약 종료 시 마지막 전달로 BPM이 원본이 되는 데 동의하는가. 종료 후 저쪽 도구의 접근권·데이터 반출 조건은.
2. **병행 기간 규칙**: 재전달 주기, 그 사이 BPM 편집 허용 여부, 충돌 시 우선순위.
3. **전달 형식 확정**: 지금 합의된 인터뷰 파일 형식으로 고정하는지. 8/9에 요청한 미결 3건(산출물 형식 초안 시점·인원 식별 기준·전달 주기)이 아직 열려 있음.
4. **오너·결재자 명단**: 업무마다 인터뷰이=오너, 결재자 계정을 산출물에 포함하는지.
5. **"이후 개선도 저쪽에서"의 뜻**: 인터뷰 산출물 보정인지, 운영 중 프로세스 개선까지인지. 후자라면 저쪽 도구에 결재·이력·권한·인사 변화 반영 기능이 있는지, 계약 만료 후 누가 운영하는지.
6. **유관부서 업무 연결 계획**: 누가, 언제, 어떤 방식으로 할 것인지.

## 9. 발표 순서 (5분)

1. 결정할 것 한 줄: 원본을 어디에 둘 것인가. (§1)
2. 초기 계획 완료, 컨설팅 대응 항목은 대부분 저희가 먼저 만들어 제안. (§3)
3. 계약 이후에 실제로 생기는 일 표. (§7)
4. 소스코드 인수는 해법이 아님, 유관부서 연결은 저쪽에 계획 없음. (§5, §6)
5. 추천안 B와 결정 요청 6건. (§4, §8)
