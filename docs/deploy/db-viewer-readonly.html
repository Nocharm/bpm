db-viewer 읽기전용 연결 9910 검증 → 운영

같은 71번 서버의 db-viewer(:6678)가 BPM의 PostgreSQL을 읽기 전용으로 보게 만드는 작업. 앱 소스코드는 바뀌지 않는다. 바뀌는 건 compose 네트워크 몇 줄 · .env 두 줄 · DB 계정 하나다. 명령 원문은 db-viewer-readonly.md.

바뀌는 것 3가지

  • docker-compose.yml — db 서비스가 전용 네트워크에 추가로 합류(이미 dev에 반영)
  • .env — DBV_NETWORK · DBV_DB_ALIAS
  • DB 안에 읽기전용 롤 dbviewer_ro

안 바뀌는 것 그대로

  • backend · frontend · nginx 코드와 이미지
  • 기존 default 네트워크 정의와 서브넷(172.36)
  • 데이터(pgdata 볼륨) — 컨테이너만 1회 재생성
  • 호스트 포트 — 5432를 새로 열지 않는다

딱 두 가지만 조심

  • docker compose down 금지 — 네트워크째 지워 다른 서비스가 죽는다. up -d db만.
  • external 네트워크는 up 전에 있어야 한다 — docker network create가 먼저.

1. 네트워크 그림 — 전용 브리지 하나를 사이에 둔다

왜 전용 네트워크인가

db-viewer 설계(그 저장소 docs/connect-sources.md)가 검토한 대안 셋 중 채택안. db-viewer가 BPM default에 합류하면 BPM이 down될 때 db-viewer 기동이 막히고, 공용망 하나에 여러 서비스 DB를 넣으면 서비스 간 격리가 깨진다. 전용망은 둘 다 피한다.

왜 별칭을 스택마다 다르게 두나

서버의 여러 서비스가 db·postgres 같은 흔한 컨테이너명을 쓴다. 운영과 9910이 같은 compose 파일이라 별칭을 .env(DBV_DB_ALIAS)로 갈라야, db-viewer가 엉뚱한 스택의 DB에 붙고도 연결 테스트가 초록으로 뜨는 사고를 막는다.

3. 작업 순서 — 7단계

전용 네트워크 만들기 서버 · 1회

겹치지 않는 대역으로 외부 네트워크를 만든다. compose는 이 네트워크를 external로 참조하므로 반드시 먼저.

docker network create --subnet 172.50.1.0/24 dbv-bpm9910

db-viewer 전제 확인 db-viewer

.env의 SOURCE_SECRET_KEY가 채워져 있고(없으면 소스 등록 503), 배포본이 마이그레이션 0015 이상(data_sources)인지 본다.

볼륨 확인 — 데이터 손실 방지 BPM

db 컨테이너는 1회 재생성된다. 데이터가 named volume에 있으면 무손실. 출력이 비면 중단.

docker inspect -f '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{"\n"}}{{end}}' bpm-9910-db-1
# 기대: volume bpm-9910_pgdata -> /var/lib/postgresql/data

.env 두 줄 + up -d db BPM

dev 코드를 받고 .env.9910에 두 줄을 넣은 뒤 db 컨테이너만 in-place 재생성. down은 절대 금지. backend는 구 DB 연결 정리를 위해 재시작.

printf 'DBV_NETWORK=dbv-bpm9910\nDBV_DB_ALIAS=bpm9910-db\n' >> .env.9910
docker compose -p bpm-9910 --env-file .env.9910 up -d db
docker compose -p bpm-9910 --env-file .env.9910 restart backend

통과: db 컨테이너 Networks에 default + dbv-bpm9910, Aliases에 bpm9910-db · /api/health ok

읽기전용 계정 BPM · psql

SELECT만 주고, 앞으로 생길 테이블에도 자동 적용되게 ALTER DEFAULT PRIVILEGES까지. 비밀번호 해시·로그인 기록·AI 원문·KB 본문은 REVOKE.

CREATE ROLE dbviewer_ro LOGIN PASSWORD '…';
GRANT CONNECT ON DATABASE processmap TO dbviewer_ro;
GRANT USAGE ON SCHEMA public TO dbviewer_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbviewer_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO dbviewer_ro;
REVOKE SELECT ON local_credentials, login_records, ai_chat_messages,
  interview_messages, interview_attachments, kb_documents, kb_chunks FROM dbviewer_ro;

통과: dbviewer_ro로 SELECT 성공 · CREATE TABLE 권한 오류

db-viewer backend 합류 db-viewer

db-viewer compose의 backend에 네트워크를 추가하고 재기동. alembic 로그가 오류 없이 head까지 찍히는지 확인.

services:
  backend:
    networks: [dbviewer, dbv-bpm9910]
networks:
  dbv-bpm9910: { external: true }

/admin 등록 → 연결 테스트 → 수집 → 허용 db-viewer UI

host bpm9910-db · processmap · dbviewer_ro. 연결 테스트 응답의 database가 processmap인지 눈으로 대조(별칭이 틀려도 초록이 뜰 수 있다). 카탈로그 수집 뒤 미리보기 허용 스키마에 public을 넣어야 값이 열린다.

통과: process_maps 미리보기에 행이 보이고 local_credentials는 권한 오류

4. 9910 통과 후 운영 승격

같은 7단계를 값만 바꿔 반복한다 — 네트워크 dbv-bpm(172.50.0.0/24), 별칭 bpm-db, 컨테이너 business-process-mgmt-db-1, 운영 .env에 DBV_NETWORK=dbv-bpm·DBV_DB_ALIAS=bpm-db. db-viewer compose에는 dbv-bpm을 추가로 나열하고 소스를 따로 등록한다.

운영 배포 규칙에 추가된 것 하나: 이 커밋 이후 운영 docker compose up은 dbv-bpm 네트워크가 있어야 성공한다. 서버 재구축 때 1단계를 다시 밟는다(setup-once.md A9).

5. 체크리스트

BPM 쪽

  • db 컨테이너 마운트에 pgdata 볼륨 확인
  • .env.9910에 DBV_NETWORK·DBV_DB_ALIAS
  • up -d db(down 아님) + restart backend
  • db Networks = default + dbv-bpm9910, 별칭 확인
  • default 서브넷 무변경 · /api/health ok
  • dbviewer_ro SELECT 성공 / CREATE 실패

db-viewer 쪽

  • docker network create dbv-bpm9910
  • SOURCE_SECRET_KEY 설정 · 마이그레이션 ≥ 0015
  • compose backend에 네트워크 추가 → up -d --build backend
  • 연결 테스트 응답 database = processmap
  • 카탈로그 수집 ready
  • 미리보기 허용 스키마 public 등록 → 행 보임

6. 자주 나오는 질문

소스코드를 고쳐야 하나?
아니다. backend/frontend/nginx 코드는 그대로다. docker-compose.yml의 네트워크 항목과 .env 두 줄만 바뀌며, 이미 dev 브랜치에 들어 있다.
기존 172.36 서브넷이 바뀌나?
안 바뀐다. default 정의는 그대로 두고 db 서비스에 네트워크를 하나 더 붙일 뿐이다. 단, networks:를 명시하면 default 자동 연결이 사라지므로 compose에 default:를 함께 적어 두었다.
db-viewer가 데이터를 바꿀 수 있나?
없다. db-viewer는 SELECT만 보내고, 계정도 SELECT만 가진다(이중 차단). 민감 테이블은 REVOKE로 아예 안 보이게 한다.
서비스가 멈추나?
db 컨테이너만 수 초 재생성된다. 그동안 앱 요청은 실패할 수 있으니 조용한 시간대에 하고, 직후 backend를 재시작해 풀의 구 연결을 정리한다.
되돌리려면?
db-viewer에서 소스 비활성화 → db-viewer compose에서 네트워크 제거 → DROP ROLE dbviewer_ro. compose 합류를 빼려면 코드 revert 후 up -d db.
